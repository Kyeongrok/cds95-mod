# 교역소 **매각** 목록 빌더와 짐 저장소 (코드로 확정)

대상: 한국어판 `대항해시대3/cds_95.exe`, ImageBase 0x400000.
(현재 파일 MD5 `06b7d581a5e6e20aa96e1256648fba18` — [[TradeSaleListBuilder-0x480CC0]] 이 적어 둔
`c2b292…` 와 다르지만 **코드 배치는 같다**. 0x480CC0 앞 int3 패딩 5개, 0x4DF0E0 문화권 표 값이
그대로인 것으로 대조했다. 달라진 건 통합수정판 바이트 패치뿐이다.)

앞 노트가 **판매**(도시가 파는 것) 빌더 0x480CC0 을 밝혔다면, 이 노트는 그 짝인
**매각**(내가 파는 것) 빌더와 그 아래 **짐 저장소**를 확정한다.
짐 배열은 절대주소로 참조되는 곳이 한 군데도 없어서(전수 스캔 결과 0건) 그동안 살아 있는
메모리 모양으로만 짐작하던 자리다. 이제 코드로 못을 박았다.

## 찾아간 길

교역 대화 핸들러 `0x481580` 이 두 목록을 나란히 만든다.

```
0x481580  TradeDialog::Open(Ctx* ecx)
  ebp = 0x480CC0(NULL,NULL,NULL)   // 판매목록 개수 (도시가 파는 것)
  edi = 0x481070(NULL,NULL,NULL)   // ★ 매각목록 개수 (내 짐)
  둘 다 0 이면 "미안하지만, 자네에게 팔 물건은 아무것도 없네."(0x532928)
  malloc(N*0x10), malloc(N*4), malloc(N*4) 후 각 빌더 재호출 → 채움
  0x481721 → 0x416120(isSell=0, …)  → 구입창을 만들어 Dialog+0xBC 에 건다
  0x48174A → 0x416120(isSell=1, …)  → 매각창을 만들어 Dialog+0xC0 에 건다
```

`0x480CC0` 과 **똑같은 count-then-fill 2패스**다.

## 함수 0x481070 = BuildSellList (매각 목록 빌더)

```c
// __thiscall, ret 0xC
int BuildSellList(Ctx* ecx, Rec16* out1, int* out2names, int* out3qty)
{
    int n = GetCargoList(NULL);              // 0x4B5780 — 개수만
    if (n <= 0 || !out1 || !out2 || !out3) return n;
    GetCargoList(out1);                      // 0x4B5780 — 짐을 out1 로 복사
    for (int i = 0; i < n; i++) {
        out2[i] = (out1[i].f3 > 0)           // 넷째 칸이 0 보다 클 때만 이름을 만든다
                ? 0x480890(out1[i].kind, -1) // 표시명 (판매목록과 같은 헬퍼)
                : 0;
        out3[i] = 0;                         // 매각 수량 초기값 0
    }
    return n;
}
```

`0x480890` 의 둘째 인자가 판매목록에서는 원산지 도시 id 인데 여기서는 **-1** 이다.

## ★ 짐 저장소 — 확정

빌더가 부르는 `0x4B5780` 하나가 짐을 전부 꺼내 온다.

```c
// 0x4B5780  GetCargoList(Rec16* out) — out 이 NULL 이면 개수만 센다
int GetCargoList(Rec16* out) {
    int found = 0, tmp[4];
    for (int slot = 0; slot < 8; slot++) {          // ★ 8 이 코드에 박혀 있다
        0x4742B0(/*ecx=*/0x5B3928, slot, tmp);      // 짐 칸 하나를 tmp 로
        if (!0x4B5730(tmp)) continue;               // 빈 칸이면 건너뛴다
        if (out) { out->kind=tmp[0]; out->count=tmp[1];
                   out->origin=tmp[2]; out->f3=tmp[3]; out++; }
        found++;
    }
    return found;
}
```

```c
// 0x4742B0  Player::GetCargo(int slot, int out[4])   ecx = 0x5B3928
BOOL GetCargo(int slot, int out[4]) {
    if (slot >= 8) return 0;                        // ★ 상한 8, 코드 상수
    int* p = (int*)((char*)ecx + slot*16 + 0x54);   // ★ 0x5B3928 + 0x54 = 0x5B397C
    out[0]=p[0]; out[1]=p[1]; out[2]=p[2]; out[3]=p[3];
    return 1;
}
// 0x4742F0  Player::SetCargo(int slot, const int in[4]) — 같은 자리에 되쓰는 짝
```

**결론 — 지금까지 메모리 모양으로만 짐작하던 것이 그대로 맞다.**

| 항목 | 값 | 근거 |
|---|---|---|
| 짐 배열 | `모듈 + 0x1B397C` (VA 0x5B397C) | `0x4742B0` 의 `ecx+slot*16+0x54`, ecx=0x5B3928 |
| 칸 수 | **8** (함대 통틀어) | `0x4742B0` 의 `cmp edx,8`, `0x4B5780` 의 `cmp ebp,8` |
| 칸 크기 | 16바이트 | `shl edx,4` |
| 칸 구성 | `{종류, 갯수, 원산지, ?}` | `0x4B5780` 의 4칸 복사 + 아래 소비처들 |

`0x5B3928` 은 플레이어/함대 전역 객체다. 짐 배열은 그 객체의 **+0x54 멤버**라서
절대주소 0x5B397C 가 코드에 단 한 번도 안 나온다 — 그래서 xref 로는 영영 못 찾는다.
`0x5B3928` 자체는 257곳에서 참조된다.

### ★ 교역소가 열려 있는 동안 짐 칸은 비어 있다

`0x481580` 은 매각 목록을 만든 **직후에 짐을 통째로 지운다.**

```
004816AE  call 0x481070      ; BuildSellList — 짐 8칸을 대화창 배열로 복사
004816B3  call 0x4B57F0      ; ClearCargo   — 그 8칸을 전부 지운다
```

```c
// 0x4B57F0  ClearCargo()
void ClearCargo() {
    int empty[4] = { -1, 0, -1, 0 };          // 우리가 "빈 칸 모양" 이라 부르던 그것
    for (int slot = 0; slot < 8; slot++)
        SetCargo(0x5B3928, slot, empty);      // 0x4742F0
}
```

물건은 그동안 **매각창 객체의 `+0xC8` 배열**에만 있고, `[결정]` 때 `0x4B5830`(AddCargo)
으로 되돌아온다. AddCargo 는 앞에서부터 빈 칸을 찾아 넣는다(같은 품목이면 합친다).

- 그래서 교역소 안에서 짐 배열을 읽으면 언제나 비어 있다. 도구가 고장 난 게 아니다.
- 그 사이에 **밖에서 짐 칸을 건드리면 안 된다.** 대화창은 여덟 칸이 다 비어 있다고 믿고
  있어서, 우리가 칸을 차지해 두면 되돌려 넣을 자리가 모자라 게임 쪽 물건이 갈 곳을 잃는다.
- MarketUtilKR 은 `0x481580` 을 MinHook 으로 감싸(들어가면 켜고 나오면 끈다) 그동안
  매매 창을 잠근다 — `Mkt_TradeOpen()`. 저 함수는 안에 모달 루프(0x481776~,
  펌프 `0x459CC0`)를 품고 있어서 진입~복귀가 곧 "교역소가 열려 있는 동안" 이다.

### 빈 칸 판정 — 게임의 공식 규칙

```c
// 0x4B5730
BOOL IsOccupied(const int e[4]) { return e[0] != -1 && e[1] > 0; }
```
**종류 != -1 이고 갯수 > 0.** 넷째 칸은 아예 안 본다 — "내구도라 0~100" 은 역시 틀린
가정이었다(해적에게 뺏은 장신구가 210 이었던 그 건). 셋째 칸(원산지)도 안 본다.

### 각 칸의 뜻 — 소비처가 증명한다

매각창 클래스(`win+0xC8` = 이 레코드 배열, `win+0xB0` = 줄 수, 스트라이드 16):

- `0x415010(row)` → `elem+0x00` 을 꺼내 `lea eax,[eax*4+0x58BAB0]` → **+0x00 = 교역품 종류**.
  (게임은 `&0x58BAB0[종류]` 주소 자체를 교역품 핸들로 쓴다. `0x42E300` 이
  `(ecx-0x58BAB0)/4` 로 종류를 되돌린다. `0x42E310` 이 쓰는 `0x58BBC8` = 0x58BAB0+70*4 —
  **70종이라는 것도 여기서 확인된다**.)
- `0x4158AE` : `mov ebp,[eax+4]` 를 보유량으로 삼아 매각량을 뺀다 → **+0x04 = 갯수**.
- 매각창 0열 `0x415185` : `[ebp+8]` 을 이름 생성기 `0x42E310` 에 넘긴다 → **+0x08 = 원산지 도시 id**.
- **+0x0C 는 아직 모른다.** 다만 `0x481070` 이 `> 0` 일 때만 이름을 만들고,
  빈 칸 판정에는 안 쓰인다.

### 매각창 열 구성 (점프테이블 0x4152DC, 0~6열)

| 열 | 내용 | 코드 |
|---|---|---|
| 0 | 품목 이름 | `0x42E310(종류핸들, 원산지)` |
| 1 | 단가 | `win+0xCC` 배열 (`0x414FB0`) |
| 2 | 중량 | `[0x4DCC2C + 종류*136]` = 교역품레코드 **+0x70** |
| 3 | 소계 | 단가 × 매각량 |
| 4~6 | (미확인) | |

교역품 레코드 base `0x4DCBBC`, 중량 `+0x70` 이 여기서도 그대로 확인된다.

## 덤으로 확정한 것 — 짐 중량 · 용량 셈

같은 전역 객체 `0x5B3928` 의 메서드들. `obj+0x34` = 기존 노트의 `함대칸(0x5B3950) + 0x0C` 다.

```c
// 0x474330  GetUsedMass()                       // 0x474430  GetUsedVolume()
sum = Σ(칸) 중량[종류] × 갯수                     sum = Σ(칸) 갯수
    + ((물   + 9)/10) * 10                           + (물   + 9)/10
    + ((식량 + 9)/10) * 5                            + (식량 + 9)/10
    + 자재 * 5                                       + 자재
    + 포탄 * 20                                      + 포탄
```
물·식량·자재·포탄 **날값 한 벌**이 `obj+0x34/+0x38/+0x3C/+0x40`
(= `0x5B395C/60/64/68` = 함대칸 +0x0C/+0x10/+0x14/+0x18) 에 있고,
중량과 용량은 **거기서 서로 다른 배수로 계산**한다.

marketdb.h 가 적어 둔 실측값 (물 5180, 식량 5180, 자재 0, 포탄 23) 을 넣으면

- 중량 = 5180 + 2590 + 0 + 460 = **8230**
- 용량 = 518 + 518 + 0 + 23 = **1059**

게임 함대 화면이 보여 준 "짐중량 8230 / 짐용량 1059" 와 **정확히 맞는다**.
→ `+0x0C~+0x18` 과 `+0x1C~+0x28` 이 각각 "중량 몫 / 용량 몫" 이라던 모델은 틀렸다.
날값은 한 벌뿐이고, `+0x1C~+0x28`(665·665·0·23) 은 다른 것이다.

함대 적재 한도(성한 배 8칸을 훑는다 — `0x4743F0` / `0x4744B0`):
- 중량 한도 = Σ `배+0x40` − (대포종류(+0x58)==-1 ? 0 : 현재대포수(+0x50) × 대포한문무게)
- 용량 한도 = Σ `배+0x44` − 최대대포수(+0x54)

즉 **대포가 먹는 몫을 뺀다.** 지금 `Mkt_Hold()` 는 `+0x40`/`+0x44` 를 그냥 더하므로
대포 실은 배가 있으면 한도를 그만큼 넉넉하게 본다.

## 값 공식 — 확정

`0x480890(종류, -1)` 이 돌려주는 값 하나가 매각가이고, 구입 단가는 그 3/2 다.

```
매각가   = 0x480890(종류, -1)
구입단가 = 매각가 * 3 / 2          (정수 나눗셈)
```

`0x480890` 은 지역 기준가 표(`0x42E3C0`)에서 시작해 도시 특산가(`도시struct+0x14`)로 낮추고,
연결 내륙도시 특산가와도 견주고, 품목 분류 보정(레코드의 분류값 2 · 5 · … 갈래)과
항로 발견 뒤 지난 날수, **그리고 시세까지 전부 반영**해서 돌려준다.
→ 부르는 쪽이 시세를 또 곱하면 안 된다. MarketUtilKR 이 한동안 그러고 있었고,
시세가 100 언저리일 땐 티가 안 나다가 130 에서 30% 부풀어 드러났다.

게임 창과 맞춰 본 것 (리스본 = 도시 id 0, 대포 = 종류 22, 특산 기준가 155):

| 시세 | 품목 | 기준가 | 0x480890 | 게임 구입창 | 게임 매각창 |
|---|---|---|---|---|---|
| 130 | 돌소금 | 22 | 28 | 42 | |
| 130 | 올리브유 | 18 | 23 | 34 | |
| 130 | 총 | 80 | 104 | 156 | |
| 130 | 대포 | 155 | 201 | 301 | |
| 127 | 돌소금 | 22 | 27 | 40 | |
| 127 | 올리브유 | 18 | 22 | 33 | |
| 127 | 총 | 80 | 101 | 151 | |
| 127 | 대포 | 155 | 196 | 294 | **196** |

`0x480890` 값이 늘 `floor(기준가 x 시세/100)` 이고 구입창이 그 `x3/2` 다. 여덟 줄 모두 맞는다.

## 남은 것

- 짐 칸 **넷째 값**의 뜻. 빈 칸 판정에는 안 쓰이고 `0x481070` 에서 `>0` 검사만 받는다.
  본 값: 리스본에서 산 대포 50개가 **100**, 해적에게 뺏은 장신구 88개가 **210**.
  0~100 범위도 아니고 갯수와도 무관하다.
- 매각창 4~6열.
- 교역품 레코드에서 **이름 · 그림 필드가 한 칸 밀려 있는 것**(칸 k 의 +0x7C 가 k+1 의 이름).
  중량(+0x70)만 칸 번호와 맞는다. 레코드 시작을 12바이트 앞으로 잡아야 맞는 듯한데
  아직 확실히 못 갈랐다. 지금은 이름 · 그림을 정적 표로 쓰므로 동작에는 영향 없다.
